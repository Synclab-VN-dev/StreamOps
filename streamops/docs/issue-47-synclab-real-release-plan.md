## 2. Artifact contract

CMake output: util/obs-multi-rtmp-websocket/release/RelWithDebInfo/obs-multi-rtmp/

Required inputs (fail closed on missing, symlink or extra files):
- bin/64bit/obs-multi-rtmp.dll — actual custom DLL generated by CMake
- bin/64bit/obs-multi-rtmp.pdb
- data/locale/en-US.ini and other validated locale INI files

Release ZIP: obs-multi-rtmp-VERSION-windows-x64.zip:
- obs-plugins/64bit/obs-multi-rtmp.dll
- obs-plugins/64bit/obs-multi-rtmp.pdb
- data/obs-plugins/obs-multi-rtmp/locale/*.ini

Separate GitHub Release assets:
- obs-multi-rtmp.release.json — exact PluginRelease contract, version from buildspec.json, source_commit from checkout, ZIP SHA256, file_count/relative_paths/tree_sha256, approved flags, OBS 32.2.1, vendor.
- obs-multi-rtmp.provenance.json — StreamOps source repo/path/commit URL, binary and ZIP SHA256, configuration, expected release tag.
- LICENSE-GPL-2.0.txt — upstream GPL license; release notes link to exact source tree and relevant attribution.

Archive paths are the exact ones understood by WindowsObsMultiRtmpInstaller, not arbitrary CMake install paths. SHA256 and file tree SHA256 are computed from actual bytes, not copied from upstream metadata. GitHub manifest metadata approved=true is set in the manually dispatched release candidate; distribution occurs only after protected reviewer gate.

## 4. One-time repository configuration (operator)

1. In StreamOps Settings → Actions secrets: add **SYNCLAB_OBS_RELEASE_TOKEN**, fine-grained credential with Contents Read/Write *only* on Synclab-VN-dev/StreamOps-OBS-Plugins. The standard GITHUB_TOKEN in StreamOps cannot publish to another repo. A short-lived GitHub App installation token is preferred in a future iteration.
2. In StreamOps Settings → Environments: create **obs-plugin-release**, require reviewers and restrict deployment branch to master. Important: a new environment with no rules is NOT a sufficient security gate; configure protection explicitly before release dispatch.
3. In managed release repo: default branch main, protect tag prefix obs-multi-rtmp/v*, disallow deletion/re-upload of production release assets, restrict who may publish.
4. Keep release credentials exclusively in protected staging/promotion jobs; PR builds never access the secret.
5. Checksums/provenance are integrity and traceability measures, NOT a cryptographic signature. Signature attestation through Synclab Signing Server can be added as another reviewed gate if required.

## 5. Runbook

1. Merge reviewed release-harness code/workflows to StreamOps master; manual workflow_dispatch definitions must be on default branch to appear in Actions.
2. Change custom plugin code/version through PR as needed. Existing OBS Multi-RTMP Plugin Build workflow validates Windows source build and produces unapproved candidate ZIP/manifest/provenance. Automatic pytest also covers packager tampering, deterministic rebuild, wrong version, missing PDB/locale and approval flags.
3. Confirm actual plugin logs/OBS 32.2.1 vendor CallVendorRequest:list_targets on a safe test machine. Validate GPL-2.0 license obligations for any redistributed custom binaries, source availability, and attribution.
4. From StreamOps Actions run **OBS Plugin - Build managed release draft**, input expected_version matching buildspec.json. It checks out master, builds source, creates four assets, runs verifier, and stages a DRAFT on Synclab managed release repo. Requires protected env approval.
5. Reviewer records source commit, DLL/ZIP hash from provenance and confirms binary/OBS compatibility, source and license. No asset uploads/replacements on an existing tag.
6. From Actions run **OBS Plugin - Promote reviewed Synclab release** with version + reviewed 40-char source commit + 64-char ZIP SHA256. Verifier redownloads exact draft assets and checks content, then flips draft=false with release token and protected environment review.
7. Windows A server environment uses STREAMOPS_OBS_PLUGIN_SOURCE_PROVIDER=github-release and STREAMOPS_OBS_PLUGIN_SOURCE_LOCATION=Synclab-VN-dev/StreamOps-OBS-Plugins. Perform read-only API catalog/preflight; protect user configs and transaction journal before mutation.
8. Publish and install v1 first → Process API restart → Vendor verify → capture SHA. Only then release v2 → Update → restart → verify → rollback to v1 and byte-compare DLL/config SHA. Test negative cases in isolated staging source rather than corrupting production assets.
